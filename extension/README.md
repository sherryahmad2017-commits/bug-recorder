# ReproFlow extension (Chrome, Manifest V3)

Phase 1 scope only: sign in, create an account, and pick a project. The capture
flow (screenshot, recording, technical context, privacy review, report submit —
features D–AJ in `docs/ARCHITECTURE.md` §3) is **not** in this build yet; it's
Phase 2 of the roadmap. This build exists to prove the auth + project-selection
plumbing end to end before capture is layered on top.

## Before you do anything: where does it point?

The API URL is baked into the build at build time from `.env`
(`VITE_API_BASE_URL`). The zip in `release/` right now points at
`http://localhost:4000/api/v1` — **it only works on a machine running the
ReproFlow backend locally.** If you upload it to the Chrome Web Store and
someone else installs it, login will fail for them, because their browser
can't reach your `localhost`.

Before a real public listing:

1. Deploy the backend somewhere public (`backend/README.md`, `docs/ARCHITECTURE.md`
   §24 — Phase 7 of the roadmap).
2. Set `VITE_API_BASE_URL` in `.env` to that public URL.
3. Add the extension's ID (see below) to the deployed backend's `EXTENSION_IDS`
   so CORS allows it.
4. Rebuild and repackage (`npm run release`).

## Build & package

```bash
cp .env.example .env      # edit VITE_API_BASE_URL if not using localhost
npm install
npm run release           # icons -> typecheck -> vite build -> zip
```

Output: `release/reproflow-extension-v<version>.zip` — this is the exact file
to upload in the Chrome Web Store Developer Dashboard (Package tab). It's a
zip of `dist/` with `manifest.json` at the archive root, which is what the
Store's upload step expects.

## Load it locally first (do this before uploading anything)

1. `npm run build` (or `npm run dev` for hot-reload while working on it).
2. Open `chrome://extensions`, enable **Developer mode** (top right).
3. **Load unpacked** → select `extension/dist`.
4. Click the ReproFlow icon in the toolbar to open the side panel.
5. Copy the extension ID Chrome assigns (shown on the card in `chrome://extensions`)
   and add it to `backend/.env`'s `EXTENSION_IDS`, then restart the backend —
   otherwise the API's CORS check will reject the panel's requests.

## Chrome Web Store submission checklist

Uploading the zip is the easy part. Google also requires, in the Developer
Dashboard listing:

- **One-time $5 developer registration fee** on your Chrome Web Store
  developer account (per-account, not per-extension).
- **Store icon** — 128×128 (already in the package; consider commissioning real
  branding before a public launch — `public/icons/*.png` are a placeholder
  brand mark generated by `scripts/generate-icons.mjs`, not final artwork).
- **Screenshots** — at least one, 1280×800 or 640×400. None are included here;
  they need to be captured from a running build once there's a flow worth
  showing (meaningfully, once Phase 2 ships the actual reporting flow).
- **Listing description, category, and language.**
- **Privacy policy URL** — required because this extension requests `storage`
  and handles authentication. Draft the policy from `docs/ARCHITECTURE.md`
  §27 (what's captured / never captured, retention, deletion, third parties)
  and publish it somewhere public before submitting.
- **Permission justifications** — Google's review form asks you to justify
  each requested permission in plain language. Use `docs/ARCHITECTURE.md`
  §26; this build only requests `storage` and `sidePanel`, so the
  justification is short (token/draft storage, and opening the side panel UI).
- **Single purpose description** — "Captures bug reports (screenshots,
  recordings, and technical context) from the current tab and sends them to
  the user's ReproFlow project." (Phase 1 alone only covers the auth half of
  that — consider whether to submit now or wait for Phase 2 so the listing's
  description matches what reviewers and installers actually see.)

None of the above are steps this repo can do for you — they happen in the
Chrome Web Store Developer Dashboard directly, under your Google account.
